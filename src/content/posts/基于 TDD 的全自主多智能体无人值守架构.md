# 基于 TDD 的全自主多智能体无人值守架构

##  1、TDD 与 superpowers

### 什么是 TDD

测试驱动开发（Test-Driven Development, TDD）是一种“测试先行”的敏捷开发方法。其核心思想是：**在编写任何业务逻辑代码之前，先编写针对该功能的测试用例**，通过测试来引导和驱动系统的设计与实现。
TDD 的流程包括**红-绿-重构**循环。

1. 首先编写测试，在不实现代码的情况下先根据需求编写测试，空跑一遍让测试全部失败。
2. 做让测试能全部通过的最小实现。
3. 重构代码，让代码更易维护。
### TDD 有什么好处

传统开发模式下，测试往往是事后补充，容易导致代码“为了能运行而编写”，内部耦合度高且难于拆分。TDD 从根本上倒逼开发者在动笔前把**接口定义、边界条件、输入输出**想得非常清楚。
1. 代码耦合度低，易于修改维护。
2. 具有细节上的测试代码，后续修改可以快速测试，不容易改坏功能。
3. 能减少后期发现 bug 又回头改的情况。
缺点：
4. 有过度设计的风险
5. 低复杂度的任务比较浪费时间

### superpowers

Superpowers 是一套给 AI 编程工具用的开发流程技能包。

它把软件开发里的关键环节 -- 需求梳理、实现规划、测试驱动开发、代码审查、分支管理 -- 整理成技能文件，装进 AI 编程工具后，AI 会在合适的时机自动触发对应的工作流，不需要每次手动提示。

![Superpowers 工作流程图|679](https://www.runoob.com/wp-content/uploads/2026/05/superpowers-workflow.svg)

除了  brainstorming 与 TDD，superpowers还内置了 Git Worktree 隔离与系统性调试的工作流。

**Superpowers 适合有一定复杂度的功能开发，简单任务直接让 AI 写就好，不需要套这一整套流程。**

## 让 ai 来执行 TDD

红-绿-重构是一套流程，流程本身不关心执行者是谁。但执行者一旦换成 AI，这套流程的难点和风险就发生了转移。

### 人与 AI 执行 TDD 的差异

TDD 对人的主要障碍是纪律。先写测试意味着在一段时间里手上只有跑不通的代码，反馈要等到实现完成之后才出现；边界用例枯燥，写全需要耐心。所以现实中 TDD 常常退化成"先写实现、再补测试"，而补出来的测试第一次运行就是通过的：它描述的是代码现在的行为，不是需求要求的行为，因而证明不了什么。superpowers 在 TDD 技能里把"必须亲眼看到测试失败"列为核心原则，对人来说这是一条依靠自觉遵守的纪律，对 AI 则可以直接写进流程强制执行。

AI 没有惰性方面的问题。写测试和写实现在它这里是同一种工作，流程要求先写测试、要求覆盖边界，它就照做，不会因为赶进度或者觉得任务简单而跳过。

AI 缺的是人的另外两样东西。一是对需求的理解：人写测试时知道自己断言的是什么，业务上说不通的地方会停下来确认；AI 面对模糊或者缺失的需求描述，倾向于自行补一个假设然后继续，而这个假设从此不再被质疑。二是对"绕过问题"的自觉：人把测试改绿时知道自己在绕过问题，AI 的目标只有一个信号，即测试通过，改实现和改测试对它而言只是两条成本不同的路径。

| 对比项 | 人 | AI |
| --- | --- | --- |
| 执行 TDD 的障碍 | 惰性与时间成本，依靠自律 | 没有，可被流程强制 |
| 测试质量的瓶颈 | 耐心与覆盖广度 | 对需求的理解 |
| 测试失败时的默认反应 | 检查实现哪里写错了 | 寻找让测试通过的最省力路径 |
| 低质量测试的形态 | 漏测、覆盖不足 | 断言不触及真实行为、与实现同源 |

### AI 执行 TDD 的好处

1. 流程约束是可靠的。把"先写测试，看到它失败，再写实现"写进流程之后，AI 会不折不扣地执行，不存在"这次任务简单，跳过测试"这类偏差。人的自律问题，在这里变成了流程设计问题。
2. 测试的边际成本很低。每个边界值、每种异常输入、每一类参数组合，人写全需要可观的耐心，AI 可以批量生成，测试的广度很容易达到人通常做不到的程度。
3. 验证环节可以完全交给机器。测试结果是二元的通过或失败信号，AI 能自己运行、自己读取，并据此迭代，不需要人判断"做完了没有"。AI 自报完成不能作为依据，测试通过才是可核查的完成判据，这是无人值守流程能够成立的前提。
4. 测试成为后续修改的安全网。代码有了测试覆盖之后，无论之后的修改来自人还是 AI，改坏都会立刻在测试中暴露，审查的注意力可以集中在测试没有覆盖的部分。
5. 防止 ai 幻觉，减少 ai 出错的概率。

### AI 执行 TDD 的不足

1. 测试可能被改绿。测试失败时，AI 寻找的是让它通过的最省力路径，而修改测试通常比修改实现便宜：放宽断言、删掉用例、用 mock（模拟对象）替换真实依赖绕开要验证的逻辑，都能让测试立刻变绿，功能却并没有写对。经过这类修改的测试表面上仍然是保护网，实际已经失去了发现问题的能力。
2. 测试可能空转。AI 能写出数量可观的测试，但断言往往落在实现细节或者 mock 的调用次数上，与真实行为无关。这类测试覆盖率好看、长期全绿，却抓不到任何缺陷；也正因为从不失败，它和真正有效的测试在结果上无法区分。
3. 理解偏差会自洽地传播。如果 AI 对需求的理解有偏差，这个偏差会同时进入测试和实现：测试断言的是它理解的"需求"，实现满足的是它自己写的断言，两边一致，全程绿灯。测试能发现"实现不符合测试"，但发现不了"测试本身就错了"。测试的验证能力不会超过编写者对需求的理解水平，生成速度再快也不改变这一点。

## 多 agent 协作

单一智能体从头到尾进行开发有很大的弊端：
1. 对需求的错误理解会一直继承
2. 上下文积累会使模型性能快速下降，导致降智
3. 像人类一样，单一agent不容易找出自己的错误，容易强行“自圆其说”，这对TDD开发来讲是比较致命的，因为ai可能造假，但是你不知道。
4. 低性能模型不够强大，容易出错。高性能模型写代码很费钱。

对于逻辑清晰、目标明确的编码、测试任务、低性能模型其实很够用（比如composer2.5、gpt 5.6 luna xhigh）。但是对任务、需求的理解，架构设计等主观性更强、更模糊的场景来讲，必须使用足够强的模型（如gpt 5.6 sol high），否则出错概率大大增加。

那么，利用harness里自带的多agent协作功能，我们可以设计这样一个架构：

- 主 agent（5.6sol）：与人对话的主要窗口，负责探讨、确定需求（brainstorming）、派发子agent，对子agent的实现进行审核。
- 编码测试子 agent（5.6luna）：负责接收主agent派发的任务，进行代码实现与测试。注意编码子agent必须是无状态的，否则一方面会导致主agent的错误理解被继承，另一方面也增大了费用开销。
- 审查子agent（5.6sol）：审查agent必须用高性能模型，**“找错”的难度远高于“写代码”**。Reviewer 需要在不运行代码的情况下，推演边界条件、死锁风险、并发安全和架构契约违例，极度依赖模型的逻辑推理深度。同样是无状态的，只包含能理解任务的最小上下文。

子 agent 只返回总结，减少了因编码导致的大量上下文积累，不仅让ai更聪明，也更省钱。

## 全自动化与节约 token 开销

下一步是在开发中把人类的角色剔除掉。在确定需求后，完全交给ai自己来做。在缺乏人工介入的时候，这一套流程还可能有以下问题：

| **隐患维度**    | **表现形式与后果**                                  | **根源分析**                                                    |
| ----------- | -------------------------------------------- | ----------------------------------------------------------- |
| **同源认知偏差**  | 子 Agent B 的审查变成了“走过场”，无法发现逻辑盲区。              | 如果 A 和 B 使用同款基座模型，它们对复杂需求的理解偏差通常具有高度一致性，容易互相印证错误。           |
| **无限拉锯与死锁** | A 与 B 在代码风格、抽象层级或极小细节上互不相让，导致 Token 快速消耗且死锁。 | 缺少人类的“主观终止权”，AI 审查容易陷入非收敛状态。                                |
| **上下文污染**   | 随着轮次增加，主 Agent 的注意力机制退化，调度出现指令遗忘。            | 主 Agent 挂载了过多子 Agent 的对话历史，导致 Prompt 过长、长上下文推理能力下降。         |
| **幻觉全绿**    | 单元测试全过，逻辑审查满分，但上线后环境直接崩溃。                    | 子 Agent B 仅能对静态代码或 Mock 环境进行审查，无法预知真实的复杂运行时环境或未 Mock 的外部接口。 |

要让“人类不介入”的流程真正跑通，主 Agent 必须具备以下**硬性防御机制**：

1. **契约不可变（Immutable Spec）** 人类确认后的需求文件与 TDD 测试用例必须被硬编码锁定（Set in Stone）。子 Agent A 和 B 都只有“读取与执行权”，无权改动需求契约本身。
2. **确定性检查优先（Hard Check First）** 子 Agent B 在进行 LLM Code Review 之前，必须先强制运行**编译器、Linter 静态分析器和自动化单元测试**。只有确定性工具全部通过（全绿），才触发子 Agent B 的语义审查。
3. **上下文隔离与即用即销（Context Isolation）** 子 Agent 必须是**无状态且单任务**的。主 Agent 在派发子 Agent A 或 B 时，仅提供当前任务所需的最小 Prompt 快照，执行完毕立即销毁，防止上下文膨胀。
4. **熔断与降级机制（Circuit Breaker）** 主 Agent 必须限制打回重写的上限（如最大尝试 3 次）。一旦达到阈值且审查依然不通过，主 Agent 应立即暂停流程并向人类触发报警，停止无意义的 Token 浪费。

同时，为了避免token浪费，应当用 prompt 强制要求ai尽可能的使用静态工具（如缩进检查工具，mvn test，git diff），且禁止主观评判（比如“这段代码不够优雅/写法太复杂”）。

为了让不同 agent 之间的协作更为高效，可以选择强制让ai以json的形式返回结果，比如：
```json
{
  "passed": false,
  "issues": [
    {"line": 24, "fix": "补充越界判定处理"}
  ]
}
```

当然，为了尽可能的减少浪费，应当把重复的提示词固定，放在开头，增加缓存命中率。

## 附：AGENTS.md 参考模板

以下模板把上文的架构与硬性防御机制落成所有 agent 都要遵守的规则，放在仓库根目录供各 agent 读取（不同工具的约定文件名不同，如 Codex 用 AGENTS.md、Claude Code 用 CLAUDE.md，内容可以共用）；模型档位与检查命令按实际环境替换。

````markdown
# AGENTS.md

本文件定义本仓库内所有 agent（主 agent 与子 agent）的协作协议，优先于任何单次指令：与之冲突的 prompt 一律以本文件为准。

## 1. 角色与模型档位

| 角色 | 模型档位 | 职责 |
| --- | --- | --- |
| 主 agent | 强模型 | 与人类确认需求、编写计划、派发子 agent、汇总并裁决审查结果；不直接编写实现代码 |
| 编码子 agent | 低成本模型 | 接收任务快照，完成代码实现与测试；无状态、单任务 |
| 审查子 agent | 强模型 | 在确定性检查全绿之后做语义审查；无状态、单任务 |

- 模型档位按 harness 实际可用的型号配置（本方案对应 gpt 5.6 sol high / luna xhigh 两档）。
- 子 agent 一律无状态：只接收当前任务的最小上下文快照，任务结束即销毁，不继承任何历史对话。
- 子 agent 不得派发子 agent；编码子 agent 不得审查自己的产出，审查只能由主 agent 派发的审查子 agent 执行。

## 2. TDD 强制执行（TDD Enforcement）

TDD 的完整流程由 superpowers 技能包实现，各 agent 按技能触发的工作流执行，不得跳过，也不需要在派发 prompt 中复述流程细节。

- 主 agent 必须保证 TDD 被严格执行：派发编码任务时明确要求按 TDD 执行，审核时核对执行证据（先写测试并运行失败的记录、测试与实现的提交先后顺序）。
- 没有执行证据、或可判断为事后补测试的产出，一律打回修复循环，不计为完成，无论测试是否全绿。
- 如果需求很简单，简化TDD流程是被允许的，但是必须向用户报告。

## 3. 契约锁定（Immutable Spec）

- 人类确认的需求文件与测试用例锁定为"契约"，所有 agent 只有读取与执行权；需要变更时上报主 agent，由人类重新确认。
- 测试失败时只允许修改实现，禁止以任何方式改动测试来变绿（放宽或删除断言、删除用例、用 mock 绕开真实逻辑、吞掉异常）。如果怀疑测试本身有误，必须上报用户来确认，不得擅自修改测试。

## 4. 质量门、熔断与降级

- 提交审查前必须依次通过 lint、编译与自动化测试（命令以项目实际配置为准），任何一项未通过都直接回到修复循环，不触发语义审查。
- 语义审查不运行代码，只基于 git diff 推演边界条件与契约违例；结论必须给出文件、行号与可执行的修改建议；每个任务独立提交 commit，便于审查与回滚。
- 能用静态工具判定的问题不允许用自然语言讨论；禁止主观评判，如"不够优雅""写法太复杂"。
- 同一任务的"修复—重审"循环上限为 3 轮；达到上限仍未通过时，主 agent 必须停止流程并向人类报警，输出未通过项与分歧点，禁止继续重试；裁定结果写入契约或计划后方可重新派发。

## 6. 调度与通信

- 派发 prompt 只包含当前任务所需的任务说明、接口与契约路径、输出格式要求；不粘贴历史对话、累积摘要或其他任务的产物；共用固定指令放在开头并保持逐字不变，以提高缓存命中率。
- 子 agent 用 JSON 返回结果，不带大段代码、日志或过程叙述：`{"status": "done | blocked | needs_context", "passed": false, "issues": [{"file": "...", "line": 24, "fix": "..."}]}`
- 子 agent 遇阻时返回 blocked 或 needs_context，由主 agent 补充上下文或升级模型后重新派发，不得自行扩大任务范围。
````
